Business flaws

HIGH · STRONG EVIDENCE

1. Authentication endpoints issue sessions without verified identity proof

OTP requests return the verification code to the requester, and Google sign-in accepts caller-supplied or fabricated profiles, so an unauthenticated visitor completes login and receives a persisted authenticated session.

Trigger

A visitor uses the public OTP or Google sign-in endpoints and supplies the identity material that the same flow exposes or accepts.

What the code does

The OTP path returns the generated code in the request flow and the Google path accepts a posted or synthesized profile, then the backend records login state and returns a JWT-backed success response.

Business rule

Sign-in must require proof of control of the phone number or a verified Google identity before a session token and user record are created.

Basis: UNIVERSAL INTEGRITY

Business downside

Unauthenticated visitors obtain signed-in access and creates or update persisted account state under chosen phone or Google identities.

Impact

Immediate outcome
The service returns successful login responses, issues JWT-backed sessions, and writes login state for identities that were not verified by an external proof step.
Affected party or asset
Authenticated dashboard access, persisted user profiles, login counters, and user-linked history state.
Scale mechanism
The behavior is reachable through public authentication endpoints and completes in the normal sign-in workflow.
Detection difficulty
Successful responses and normal login records look the same as legitimate sign-ins.
Reversibility
Issued sessions expire later, but created profiles, login counters, and stored history require explicit cleanup.

How the code reaches the outcome

  • The backend exposes public POST routes for /api/auth/send-otp, /api/auth/verify-otp, and /api/auth/google.
  • The OTP send handler returns the service result from createAndSendOtp, and that service includes the generated code in its returned object; the frontend also reads backendRes.code and surfaces it in the request flow.
  • The OTP verify handler only checks that the submitted code matches the stored session, then records login state and returns a JWT and user object.
  • The Google login flow posts either the Firebase popup result or a synthesized fallback profile to the backend, and the backend accepts req.body.profile or creates its own default profile, records login, signs a JWT, and returns success.

What to change

Require independently verified identity evidence before issuing an authenticated session or persisting login state.

Acceptance check

Given an unauthenticated caller who can reach the public authentication endpoints
When the caller reads the OTP from the request flow or submits a fabricated Google profile and completes the corresponding sign-in request, the application returns a successful authenticated response and records the login as that identity.
Then the sign-in is rejected unless the caller presents externally verified proof for the claimed phone number or Google account
